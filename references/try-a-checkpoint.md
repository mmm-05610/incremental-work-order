# 把检查点跑起来给用户试用（调度者的活）

**原则**：检查点本身只是 tag + 报告；"**能试**"需要一个可运行的链路。这条链路**属于调度者**，
**不要写成执行者的工单**——它不是产品开发项，会挤掉队列里的真活，而且往往要碰用户的环境（装依赖、起服务、开窗口）。

## 五步

1. **读检查点报告**：拿到"能试什么"与"未跑"两段——后者通常就是缺的运行时（缺二进制、缺服务、缺数据）。
2. **先核环境，不要给跑不通的命令**：二进制在不在、端口有没有被占、数据根是否被锁、显示是否可用（WSLg/X11）。
   所有命令都**先自己跑一遍**再交给用户。
3. **分半边验真**：**服务端先起并验真**（用真实方法调用，看到"参数错"而不是"方法不存在"就说明方法在），
   再处理应用/客户端那半边。半边能用就先交付半边，别等两半都齐。
4. **不碰用户的凭据与既有进程**：用**独立数据根**与**不同端口**，避开用户正在用的实例；
   导入凭据这类副作用先问。
5. **沉淀成 runbook**：把可用的命令、踩过的坑（端口/数据根锁/参数形状/依赖 token 名）、"看什么+反例"写进仓库，
   下次照着跑。缺的那半边**如实写明待确认**，不要猜。

## 与工作流的关系

- 试用里发现的问题 → 主树 status 记一行"待派" → **当日**写成工单投递（v2、过校验器）。
- 试用**不打断**执行者的批次节奏；要立刻改方向走"追加 / 插队 / 改向"三档。
- 试用链路的修复**不占执行者队列**；若确实需要产品代码改动，才写成工单。

## 反面教材（本工作流踩过的）

- 让用户自己去某个文件里复制命令（应**在回复里给全原文**）。
- 交出一串没验过的命令（括号没引号、二进制路径猜错、bundle 版本过期）。
- 用"假数据/模拟服务"冒充"真实应用 + 真实后端"的联调。
