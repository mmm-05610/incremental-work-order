# 反假绿清单

"绿得可疑"比"红"更危险：红会逼人处理，假绿会被当成已完成写进账本，后面所有依赖它的事都建在沙子上。
派单、验收、和检查点交回时逐条过。

## 清单

1. **资源缺席时是什么颜色？** 前置检查、扫描、守卫在"目标不存在 / 打不开 / 结构未知 / 版本不匹配"
   时**必须失败**（类型化拒绝优先于静默换地方）。"没找到东西所以跳过"= 假绿。
2. **守卫证明过自己能抓到正例吗？** 只有"零命中"不是证据。每个守卫至少配一条**人为制造命中**的反例；
   抓不到正例的守卫等于没有守卫。
3. **读的人真的能看见数据吗？** 打开方式、过滤条件、快照时机都可能让"零命中"变成结构性失明
   （见例 2）。守卫要断言"我读的是写者写的那份"。
4. **文档与代码矛盾有没有被测试钉成绿？** 文档声称 A、代码是 B、测试断言 B 通过 ⇒ 矛盾被固化。
   按缺陷修（补 A 或改文档），不要只在账本里记一笔。
5. **门跑了吗？** 没跑就写"未跑"；缺样本导致的部分覆盖写"部分覆盖 + 剩余项"。
   **PARTIAL 不得写成 DONE**，缺项要逐条列。
6. **断言强度有没有为了变绿被放宽？** 改断言、降上限、加 skip、改成"至少不报错"都算放宽；
   放宽要么有明确授权，要么算返工。
7. **计数与摘要对得上吗？** 回归计数、摘要（digest）、行号引用要能就地复算；沿用旧数字必须标明来源与时间。

## 例 1：缺席即通过

一个"前置检查"在部署里找不到被检查的对象时直接返回通过。结果是：**最该被拦的状态（配置缺失）
反而是唯一能过门的状态**。修法：缺席走类型化拒绝，并补一条"人为去掉目标 ⇒ 必须失败"的反例。

## 例 2：读的人看不见数据（结构性失明）

守卫用只读方式统计某张表，结论"零命中、干净"。但该库处于 WAL 模式，**尚未 checkpoint 的写入对
这种只读方式不可见**：先 checkpoint 过一次、再把一行只写进 WAL，这种读法会读出 0 行，而正常读法
读出 1 行。⇒ 守卫必须读穿 WAL（或先确认写者已停），并且**反例是**"先写一行、不 checkpoint，
守卫仍须命中"。判据不是"我读到 0 行"，而是"我能看见写者写的东西"。

## 例 3：矛盾被测试钉成绿

文档说"能力矩阵已按门证据回填"，代码里该项仍是"未观测"，而汇总测试断言的正是"未观测是空集"——
**测试把矛盾固定住了**。方向保守（少报能力）所以不影响安全，但这类不一致正是本项目最不允许的。
修法：按门证据回填 + 同时改断言，不留"文档与代码各说一套、测试替其中一套背书"的状态。

## 交回时的写法

- 每道门写全三个要素：**断言** / **反例（必须存在）** / **缺席与未知时的行为**；Gates 表共四列（含门名列），每行填满。
- 缺任何一列的门，在检查点报告里标"未证明"，不要写成通过。
